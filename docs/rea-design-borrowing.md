# 用 REA 拆经典 App 的设计

> 记录于 2026-10-19。想法来自用户：能不能用 REA 这类逆向工具分析经典 App，把里面好的设计借鉴过来。

## 一、REA 是什么（事实，非宣传）

- 仓库 `morluto/rea`（官网 rea.tools），MIT，作者 morluto；2026 年 4 月建仓，10 月爆火。
- 形态：**MCP server + CLI**，把逆向工具接到 Claude Code / Codex / Cursor 这类 agent 上。分析全部在本地跑，不上传目标文件。
- 能拆的目标（与我们相关的）：
  - **Android APK**：无头 JADX 反编译到方法级，读 manifest、类结构、每个方法的逻辑；6.4.0 起有 ADB 设备工具（列应用、拉取 split APK、看日志、截屏）。
  - **网站**：驱动 Chrome 系浏览器，拿页面结构、脚本、网络行为。
  - **JavaScript / Electron**：模块、imports、路由、IPC，静态分析，不需要反编译引擎。
  - **原生二进制**：伪代码、汇编、符号表（需要 Hopper / Ghidra / IDA）。
  - **HAR 抓包**：请求、响应、payload 来源位置。
- 本机现状：Node v26.7.0 ✓（REA 要求 26+）；JDK 11 ✗（JADX 要 17+，得先装）；Ghidra 未装（只在拆原生二进制时才需要，拆 APK 不需要）。

## 二、能不能用：能，但只能拿到三层里的一层

拆一个 App 能得到的东西分三层，价值差得很远：

| 层 | 内容 | 拿到的手段 | 价值 |
|---|---|---|---|
| 视觉层 | 颜色、圆角、字号、间距、图标 | 截图 + 取色 | 低，杀鸡用牛刀 |
| **交互层** | **手势仲裁顺序、状态机、阈值、去抖、回弹曲线、动效常数** | **反编译 + 读布局/动画资源** | **高，这是我们最贵的试错成本** |
| 意图层 | 为什么这么做、当时在解决什么用户问题 | 拿不到，任何工具都拿不到 | — |

**结论：REA 不是「抄设计」的工具，是「拿到别人已经调好的参数和仲裁顺序」的工具。**
它省掉的不是画图时间，是「我们调三天还是觉得不对劲」的那部分。

## 三、对 Daymark 真正值得问的三个问题

不是「它长什么样」，而是：

1. **手势仲裁**：列表/卡片上的滑动翻页，怎么和卡片内部手势共存？——谁先抢指针、slop 多大、方向判定先横还是先纵、哪个子元素豁免。我们这轮踩的坑（撤掉删除后卡片吞手势）正是这一类。
2. **动效常数**：按下、翻页、弹层的 duration 与曲线；多元素位移的错峰；松手回弹的 spring 参数。
3. **失败态与空态**：数据为空、离线、权限被拒时怎么说、给什么下一步。这三屏最能看出一款 App 的成熟度，也最容易抄。

## 四、目标清单（拆谁、拆什么）

| App | 拆哪一层 | 具体想看什么 |
|---|---|---|
| **Streaks** | 交互 + 文案 | 连续记录的呈现方式；断签了怎么说（不惩罚的表达） |
| **Things 3** | 交互 | 卡片点按 → 编辑的进入方式；拖拽与滚动的仲裁 |
| **Duolingo** | 交互 + 节奏 | 奖励密度、庆祝节点、错过之后不羞辱用户的做法 |
| **Forest / 养成类** | 视觉 + 曲线 | 角色成长的可视化层级，与「还差多少」的表达 |
| **Apple 健康 / 健身** | 表达 | 数字怎么显得可信、有分量（大数字旁的信息权重） |
| **Bear / Fantastical** | 交互 | 列表 ↔ 编辑的过渡，弹层高度与安全区处理 |

## 五、执行步骤（一次约 3 小时）

1. **准备**：装 JDK 17+ 与 `jadx-headless-mcp`；跑 `npx rea-agents setup` 把 REA 注册到 agent。
2. **取包**：只对自己安装/合法持有的 App —— 用 REA 的 ADB 工具从设备拉取，或用官网提供的 APK。
3. **固定三问**（每次拆都问同样三句，便于横向比较）：
   - 这个交互的手势优先级是怎么排的？
   - 这几个动效的 duration / 曲线 / spring 参数是多少？
   - 空态、失败态、权限被拒时它写了什么？
4. **产出**：`docs/teardown/<app>.md`，只记「参数 + 仲裁顺序 + **我们改成了什么**」。
5. **验收**：每份拆解必须落成至少一处对 Daymark 的具体改动，否则这份拆解不算完成。

## 六、边界（说一次，不再重复）

- 取**参数与思路**，不取素材、字体、图标、代码；工具的 MIT 协议不改变对方 App 的用户协议与著作权。
- 只拆自己合法持有的 App，不绕过付费墙、不破解、不重新分发。
- 反编译出来的业务逻辑不能直接搬到我们的 PWA：平台不同，**参数可以迁移，机制不一定**。

## 七、我的判断

**值得做，但不要做成「批量抄设计」的项目。**

建议先只做两个：**Streaks**（打卡的表达与不惩罚）× **Things 3**（编辑过渡与手势仲裁）。
判断标准很简单：拆完如果没让我们改掉任何一行代码或一个参数，说明方法用错了，立刻停。

另外提醒一句：这套方法最大的风险不是合规，是**审美依赖** —— 拆多了会开始照着别人的答案做题。
拆解的正确用法是「验证我们想做的事有没有更省的实现」，不是「先看看别人怎么做再决定做什么」。
顺序一旦反过来，产品就没了。
