# Daymark · 刻度 —— 产品方向

> 记录产品经理 2026-10-21 提出的产品想法，以及对这些想法的拆解、张力与取舍。
> 这是方向讨论稿，不是排期；任何一条落地前仍需单独过方案。

## 一、产品想法

定位是**中性的、有亲和力的侧重自律打卡和记事提醒类工具**。

1. **亲和力与定位**：中性偏可爱卡通的萌系审美，男女通吃。
2. **首套造型**：卡通可爱风；萌系作为造型语言，**不等于**「粉色 + 手写体」——这类刻板符号。
3. **主题体系**：支持多套主题风格，各类审美一网打尽，支持主题自定义；首套以可爱卡通为主，后续可扩展其他完整风格包。
4. **注意力聚焦**：一次只能聚焦在一个打卡或重要事件上，但允许切换注意力。
5. **手势**：横向滑动用于浏览和切换风格。
6. **相片背景**：允许上传相片作为事件的背景。
7. **情绪价值**：深挖情绪价值。
8. **产品气质**：用做游戏的思路来做这款应用。

## 二、逐条拆解

### 1. 中性偏萌系（亲和力定位）

产品底色仍是**自律打卡与记事提醒**，萌系是让人愿意天天打开的亲和力，不是换一套人群标签。

对功能和文案，保留三条判断标准：

- **去绩效化**：断了、放弃一轮，不被惩罚或羞辱（红字、断签、排名）。
- **造型本身算功能**：字体、留白、封面、语气，不是装饰。
- **可分享**：分享是这类产品最自然的传播路径。

在工具框架里，这条的含义是：**提醒与记录仍然清晰可用**，同时用造型和语气降低冷冰冰的「任务感」；萌系是亲和力最直接的载体。

### 2. 卡通可爱风（首套皮肤）

与当前审美（深色、几何、Inter、克制）是两个人格，不是微调。

可行的做法不是二选一，而是**风格包（Theme Pack）**：同一套信息结构，皮肤层可替换。

- 需要先抽象出「皮肤」接口：色彩令牌、圆角、字体、卡片材质、装饰物、背景、动效曲线。
- 现在的 CSS 变量体系（`--surface` / `--text-3` / `--radius-card` / accent 色板）已经是雏形，缺的是「一套皮肤 = 一份令牌文件」的组织方式。
- 风险：可爱风会削弱「大数字」的仪式感；需要在皮肤里单独设计数字的呈现（例如手绘数字 vs 现在的渐变数字）。
- 萌系的可动载体比配色更重要。

### 3. 主题自定义（多套风格包，首套可爱卡通）

目标是**各类审美一网打尽**，不是给一套皮肤换颜色，也不是只服务「可爱」这一种人格。所以入口形态也跟着变了：
需要一个**能看见多套皮肤、并能快速对比**的地方（见第 5 条）。

### 4. 注意力聚焦：一次只有一个，可切换

也是八个想法里最有产品价值的一条。

**聚焦的是当前展示，不是数据**：库里仍可有多个打卡与提醒；界面上**同一时刻只强调一件**，用户可以随时**切换注意力**到另一件（钉选 / 点选），而不是被锁死在唯一一条上。

现状：三页并列列表，一屏能放 2–3 张卡，注意力是摊平的。

### 5. 横滑：浏览与切换风格

横向滑动用于两类体验：**在内容之间浏览**（翻页、看多件），以及在**主题体系里切换风格**（预览、对比、应用皮肤，承接第 3 条）。画廊或预览区内的横滑与首页纵向滚动要分工清楚，避免同一方向叠多种含义。

### 6. 上传相片作为背景

技术上可行，但要先解决存储，这是硬约束：

- localStorage 只有 ~5MB 且同步写，放不下照片。**必须引入 IndexedDB**（`idb` 或无依赖的薄封装）。
- 上传后在 canvas 里压缩体积再写入本地存储。
- 相片会直接影响文字可读性，需要考虑用遮罩或模糊化和局部高清进行设计。

### 7. 深挖情绪价值

这是前几条在体验上的总纲。可以落地的方向：

- **语言**：现在的文案偏工整（「按住卡片记一次」「已经走过的日子」）。情绪价值来自具体的、非功能性的句子，例如「今天也可以什么都不做」。
- **被看见**：记录本身要被「回应」——第 7 天、第 30 天、断签后回来，各有一句话，而不是只有数字。
- **结束的仪式**：一轮结束时（重置/删除/到期）给一次告别，而不是一条 toast。
- **可分享的产物**：一张卡片截图（背景 + 数字 + 一句话），这是这类产品最重要的传播单元。
- **不要做的**：社区、排行榜、连续天数惩罚、红色警告。以正向激励为主。

### 8. 用做游戏的思路来做这款应用

这条不是第 8 个并列的功能，而是**第 7 条的方法论**：情绪价值在游戏里已经被验证了三十年，
不必从零发明。

先划清界限，游戏化有两个截然不同的方向：

- **压力型游戏化**（体力值、连续签到惩罚、排行榜、限时任务）：它把打卡变成 KPI，和「去绩效化」直接冲突。**不做。**
- **反馈型游戏化**（成长、收集、惊喜、仪式、角色）：它放大「被看见」，正是第 7 条要的东西。**主攻这个。**

游戏设计能给这个应用的六件东西：

1. **核心循环**：现在的一次打卡 = 按下 → 蓄满 → 数字 +1 → 特效 → 结束，循环到「结束」就断了。
   缺的是**回头看的理由**：一次记录之后，玩家会想看「我的小东西变了吗」。
2. **养成角色**：每件坚持的事都该有一个**会长大的东西**（第 2 条萌系的落点）。
   连续 3 / 7 / 30 / 100 天各进化一次形态；断了不退化（去惩罚），只是停止生长。
   这一条同时解决「萌系除了换颜色还能做什么」和「情绪价值怎么看得见」。
3. **章节与图鉴**：一轮坚持 = 一章；重置/结束时归档，进入「藏馆」。历史不该只是一列数字，
   而是一个可以翻的过去。这正好复用现有的 streak 归档数据。
4. **收集**：里程碑徽章、节庆、年度回顾、皮肤——收集物是皮肤体系天然的配重。
5. **惊喜**：低频、不可预测的小彩蛋（第 7 天的一句话、某个节日的隐藏动画）。
   注意别做成老虎机：**不设概率奖励、不设稀缺、不诱导重复行为**。
6. **过场**：里程碑可以有 1.5–2 秒的过场（可跳过）。但按项目已有的真机教训，
   **过场只挂在低频节点**（里程碑、章节结束），日常打卡仍然是 3 个动效节点封顶。

一句话：**用游戏的反馈结构，不用游戏的压力结构。**

## 三、依赖关系（先做什么）

```
风格包体系（皮肤接口）
   ├── 2 卡通萌系 ─┐
   ├── 3 多套主题   ┼── 5 皮肤画廊（横滑预览）
   └── 6 相片背景   ┘
焦点卡（4）
   └── 承载 7 的情绪文案与相片
养成角色 / 章节图鉴（8）
   ├── 复用 streak 归档数据
   └── 是萌系皮肤的主要载体
IndexedDB（6 的前置）
   └── 相片背景 → 分享截图
```

结论：**风格包体系是这一批想法里唯一的基础设施**，不做它，2/3/5/6 都会变成散装特判。
